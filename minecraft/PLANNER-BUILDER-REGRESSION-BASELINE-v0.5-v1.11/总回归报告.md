## L0 → L4 recursive planning coverage

这里的L0–L4指**规划尺度**，不是代码工程的L0–L3四层依赖架构。

| 规划尺度 / 交接 | 证据 | 已验证关系 |
|---|---|---|
| L0 POLITY_TERRITORY → L1 REGIONAL_SYSTEM | P01R `implementation-packages.json` | 四个下层Planner包；parent/child scale、recipient、固定/待解/可变/修订字段；非Builder-ready |
| L1 REGIONAL_SYSTEM → L2 SETTLEMENT | P02R 同名包文件 | 三个聚落Planner包；地表差异、条件容量与交换网络继续收敛 |
| L2 SETTLEMENT → L3 DISTRICT | P03 同名包文件 | 三个街区Planner包；内部流、共享空间、供水及基底条件进入下层 |

| L3 DISTRICT → L4 URBAN_ENSEMBLE | P04 `implementation-packages.json` | 三个组团/公共协调包；家庭、公共院、门前、后巷关系分工明确 |

## Planner → Builder handoff coverage

MP-I01先证明WHY / Program / Flow / Rights与建筑推理兼容，同时暴露“路线ID+名义宽度”不足以冻结设计。P05R2原始BDP实际具备：revision/readiness、design与causal context、显式parcel cells、`CELL_CENTER_MASK`、fixed/adaptable、局部Interface Baseline、nominal与minimum clear区分、断面/高程、可调范围、权利、coordination owner、外部服务责任、direct dependency hashes及`resolve_before`。

MP-I01R仅消费目标BDP及直接依赖，形成Plan + Section + Sequence、低作坊/高住屋、独立家庭廊与私院。建筑作者权仍属于Builder；接口信息更完整没有把Planner变成单体设计者。面对`CONCEPT_DESIGN_READY`，它保持`CONCEPT_DESIGN_WITH_INTERFACE_HOLD`，没有再把已给出的几何误报为缺失，也没有回读完整上游来补答案。

MP-P05R原始`planning-data.json`仍可见`state=SCOPED`同时`builder_ready=true`，其BDP缺少目标合同字段；这支持原审核的执行失败分类。P05R2输出及来源记录修正了该复跑样本，**没有抹掉P05R的失败，也不能据一次成功保证未来模型绝不漏加载Skill**。

## Builder → Planner revision / escalation coverage

已验证的局部闭环是：

```text
P05R2 BDP-01 r1 / CONCEPT_DESIGN_READY
→ I01R concept r1 / Interface HOLD
→ I02A BDP r2 + LANE-04 / THRESHOLD-1 / RAINWATER r2
→ concept STALE_FOR_FIDELITY_REVIEW
→ I02A2 BDP r3 + 同一受影响接口 r3 / DESIGN_FREEZE_READY
→ I02B重检r3，保留主体，只深化必要细部
→ 新UPSTREAM_PLANNING_ISSUE：MP-I02B-UPI-RAIN-01
```

两份revision-lineage原始记录均只改受影响对象；未受影响接口保持revision，Planner未修改Builder设计。I02A未满足闭合目标，被审核记为PASS_WITH_FINDINGS；I02A2补齐50列连续公共扫掠、转角、两端接续、Y132接触及逐格保护断面。

I02A2还分开了task-local规划协调角色与真实土地/地役许可，并固定禁止默认跨界排水、公共受纳义务NONE、Builder负责本户闭合性能。这关闭的是规划责任悬空，不是水力证明。I02B比较本户有界方案后提出新问题，而非静默发明公共出水口。**该新问题后续获接收、再次修订并最终冻结的第二次完整闭环未在本基线中验证。**

## Planning Fidelity coverage

原始`Planning-Fidelity-Gate.json`逐项包含WHY、Program、Flow、Rights、public/private threshold、parcel boundary、public clear envelope、terrain response、Planner Fixed、uncertainty/resolve_before、external services与Builder authorship。

I02B保留一户容量、低肩角色、独立家庭生活与私院、公共横通及地下保护；564个候选原生状态在151列mask内，公共包络侵入0，18格私院和Y132接触保持。六条路线806次静态身体包络检查无障碍，是已有几何证据，**不是本次新跑Minecraft或新的运行时认证**。

Fidelity行为经独立审核认可，但建筑自己的Gate仍为`UPSTREAM_PLANNING_ISSUE`，不是PASS。套件对“Gate正确执行”的认可与“该设计通过Gate”是两个不同判定，不能合并。

## Builder Design Freeze behavior

I02B正确把Planner的`DESIGN_FREEZE_READY`理解为可尝试冻结的输入条件，而非建筑自动就绪。它保留MP-I01R已成立的意图、主体平剖面、Program、Massing和石木逻辑，局部细化门、屏、护栏、窗与器具，形成candidate r2。

| 条件 | 已有结论与下一责任 |
|---|---|
| U-GROUND | 实际编辑/接触与浅层筛查已有；真实荷载影响边界、承载/节理及相关既有结构范围不足，仍是Builder / site evidence blocker |
| U-HABITABILITY | 两住户是design occupancy，不是实际人口；生活功能和独立路线有空间，但炊火/排烟等未闭合 |
| B-TRANSLATION | 大量原生状态已明确；实心烟囱不是净腔，泛水/收水链和动态交互仍未认证 |
| B-RAINWATER-PERFORMANCE | 有限蓄水不能在无累计事件、恢复机制、安全失效边界时证明永久闭合；返回新的项目级上游问题 |
| B-PLANNING-FIDELITY | 已消费r3并重检，未机械发PASS |

已验证的是**负向冻结控制：证据不足时拒绝虚假DESIGN_READY**。正向`DESIGN_READY`成功样本尚未实证；不得补写为通过。41项I02B交付检查、I02A的17项、I02A2的31项和P05R2的50项一致性检查都是原归档记录，支持产物一致性，不替代工程或语义验收。

## 当前限制与 Known limitations

- BDP-01的地基、烟道/防火/居住环境、雨水性能是当前建筑与场地证据未闭合，不是已有审核支持的foundational Skill failure。雨水的项目要求必须具有有限、可验证的设计基准；必要时由项目规划/Owner修订服务边界。
- 实际地权/地役及施工批准仍在`BEFORE_WORLD_WRITE`；供水/食物/燃料能力在`BEFORE_PERMANENT_OCCUPATION`；污物终端、搬运和运营责任在`BEFORE_OPERATION`。本报告不关闭它们。
- Surface不等于substrate；浅层未见空气不等于承载、无深部内容或可施工。历史世界哈希只覆盖当时获准读取的文件，不是全存档或当前世界的认证。本轮没有打开存档。
- 有效通达、季节供给、运输模式、容量上限和吞吐假设尚需各项目验证。规划图、BFS、静态碰撞盒、零越界不能替代原生邻接更新、连续步行、流体和保存/重载测试。
- 正向DESIGN_READY、Builder Core、SPATIAL_COMPLETE、Finishing、最终世界交付均不在已通过覆盖中。不能把这条核心接口链说成完整Builder生命周期回归。
- 主要场景集中于CIV-001山地混合前沿及一户Builder案例；没有穷尽其他文明、地形、建筑类型、并发接口修订或多轮升级。
- 部分早期测试不是全新会话级盲测；若干Independent Review没有独立逐像素/实机视觉审核。本次只整理既有证据，未新增视觉或独立工程认证。
- 约250KB的P05R2整包存在体积/重复成本；I01R已验证按ID和direct refs选择性消费。当前没有证据要求为此修改合同，但不能保证大规模任务永不发生上下文膨胀。
- P05R表明执行/加载失败仍可能发生。稳定版本不等于模型执行必然正确；来源版本和交付合同仍应核验。

## Production usage recommendation

推荐把这三个固定版本作为**规划与设计协作的稳定起点**：按真实任务取得当前批准Canon与必要场地证据，保留尺度、source/currentness、直接依赖与`resolve_before`，按既有合同消费与回报问题。该建议不改变任何Skill规则。

本案不需要为了让回归“看起来全绿”修改通用Skill。若继续建筑，应先解决本案可验证的工程与雨水设计基准，再重跑受影响的设计Gate。若补充套件覆盖，优先单列证据完备的正向DESIGN_READY fixture；这是未来建议，本轮不创建任务、不执行测试。

任何实际施工仍需独立的目标存档、revision/hash授权及适用执行验证。稳定基线不授权Builder跳过设计冻结、写世界或修改正式项目。
