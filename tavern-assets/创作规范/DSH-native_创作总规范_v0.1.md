# DSH-native 创作总规范

本规范是仓库全部世界包、人物卡、拓展包创作的通用纪律。它取代旧创作规范中绑定第二版 SillyTavern Runtime 架构的全部内容，继承其中与架构无关的创作纪律。

## 〇、效力与权威来源

- 本规范当前为**讨论稿（draft）**，经项目所有者定稿后转为 current。
- 目标宿主：**The World on DeepSeek Harness (DSH)**。资产消费侧语义的唯一权威来源是 `zhangchenjia21-dot/the-world` 仓库的：
  - `docs/PRODUCT_SPEC_CURRENT.md`（产品语义：Composition、T0、知识边界、节奏、授权粒度）；
  - `docs/ARCHITECTURE_CURRENT.md`（工作区与恢复语义：Source / game-local 分离、durable maintenance）。
- 创作任务开始前必须重新读取上述权威文档的 current 版本；宿主语义变化时本规范随之修订。
- 本规范不定义、不假设任何机器协议。不为 Creator、asset-spec、Resolver、Bootstrap、Validator、Manifest 预留字段或格式。

## 一、宿主语义基线

以下是 the-world 已冻结、资产创作必须对齐的语义。资产正文不重复解释这些机制本身，但写法必须与之兼容。

### 1.1 Source 与 game-local 分离

- 资产（Source）定义**开局之前**的世界：既成事实、默认轨迹、可复用素材。
- 开局后 `games/<game-id>/` 是活的本局现实；局内变化永不回写 Source。
- `game-local reality > source default trajectory`：原史 / 原设是参照，不是未来事件队列；已发生的分叉不得被静默修正回 Source。
- 推论：资产正文**不得预写未来**（未来的死亡、战役、背叛、统一、结局），无论是以"剧情"还是"后台事实"的形式。

### 1.2 Game Composition 由玩家确认

- 新局的 World / Player Character / Expansion / 主角操控粒度由玩家逐项确认，确认前不进入正式叙事。
- 世界包可以用自然语言声明 **Required / Recommended / Optional** 分级建议；Optional 默认关闭，只能由玩家明确启用。
- 资产只提供"我是什么、我为什么值得启用"的信息；**启用决策永远属于玩家**，资产不得写成静默自激活。

### 1.3 知识来源边界

- `GM / Source / System knows X ≠ NPC knows X`。
- NPC 可用的信息必须能由世界内来源解释：亲历、身份 / 职业渠道、被告知、传闻、可观察事实、合理推断、显式超自然权限。
- 资产的职责是**标注**信息暴露层级（公开 / 仅 GM / 角色私有 / 未来不可知）；边界的执行由 World Core 负责，资产不实现传播控制。

### 1.4 Unlimited Attempt 与后果归属

- `Player owns Attempt；World owns Consequence；GM owns Playability of the Consequence`。
- 机制资产写裁定语义，不替玩家决定行动；技能、身份、机制列表**不是玩家输入白名单**，不得写成"只能这样做"。

### 1.5 双循环节奏

- 世界同时存在 World Loop（局势→事件→后果→时间推进）与 Life Loop（日常、互动、关系与人格积累）。
- 人物卡与世界包必须为 Life Loop 提供素材（日常、嗜好、非功能性互动面），不能只写功能性能力清单。
- 节奏控制本身是 GM / World Core 职责，资产不内嵌节奏状态机。

### 1.6 主角授权粒度

- Full Control / Light Delegation / Narrative Delegation 由玩家选择，共同原则是"压缩无效时间，在有意义的抉择处停下"。
- 人物卡若支持玩家接管，写明 T0 前哪些已锁定、T0 后哪些选择权归玩家；不替玩家预设重大承诺、阵营与不可逆路线。

### 1.7 重要性决定注意力，不决定存在

- 运行中产生的人物、关系、承诺、后果一旦形成 durable fact 就应被记住。
- 资产写作推论：不要把次要人物、普通地点写成"用完即弃的道具"；为高稀有度资源（名臣、神物、禁术）保持稀缺性，不写成像廉价供货。

## 二、通用结构约定

### 2.1 三类资产的统一骨架纪律

每份资产都以**定位声明**开篇、以**关系与修订**收尾：

```text
开头：这份材料是什么 / 这份材料不负责什么
正文：领域内容
结尾：与其他资产的关系 → 相关资产 → Revision Notes
```

- 世界包体量最大，用中文数字大章（一、二、三……），章内用 `N.M` 小节；
- 人物卡、拓展包用阿拉伯数字编号节；
- 拓展包开篇使用双 callout：`> [!abstract] 这份拓展包是什么` + `> [!important] 启用方式`。

### 2.2 Frontmatter 最小集

Frontmatter 只是人工治理元数据，不是机器 Schema。必填字段：

```yaml
title / status / version / asset_family / tags
```

按类型补充：

- 世界包：`aliases / created / updated / asset_type: world-pack` + 世界语义属性（如 `historical_mode`、`supernatural_default`、`language`）；
- 人物卡：`aliases / type: character-card` + 人物属性（`historical_character`、`birth_year`、`player_character_supported`、`research_note`）；
- 拓展包：`aliases / created / updated / asset_type: expansion-pack`。

**禁止**出现机器绑定字段（`creator_binding`、`asset_spec_binding`、`workflow_mode` 等旧体系占位）。

### 2.3 资产间引用

- 统一使用 **Markdown 相对路径链接**，不使用 Obsidian `[[wikilink]]`。
- 正文中提到其它资产时用书名号《资产名》称呼，并在"相关资产"节给出相对路径链接。
- 既有资产中的 wikilink 残留属已知遗留，随各资产下次修订时顺手清理，不单独批量替换。

### 2.4 版本与修订

- 语义化版本 `vX.Y[.Z]`：措辞澄清升 patch 位，结构性改版升 minor 位。
- 文末固定 `## Revision Notes`，每条以 `vX.Y.Z（一句话主题）` 起头，下挂 3 条左右短要点。
- 被取代的旧版本用 `supersedes` 记录并移入归档；active 目录同一资产只保留一个 current。

## 三、知识边界与信息分层

### 3.1 世界包：按可见层级组织

世界包必须显式区分三层信息：

1. **玩家可见的公开事实**：当前政权、当地官府、已传开的名人声望等——需按开局年份、身份、所在地筛选；
2. **仅 GM 与本包掌握的事实**：未传到的远方事件、真实归属、一致性维护事实——用于制造信息差，不得泄露给角色；
3. **永远不能预写的内容**：未来的死亡、战役、称帝、背叛、统一，一概不得以任何形式预写。

### 3.2 人物卡：按"凭什么知道"组织

人物卡的知识节以一条总纲开头——"这个人物只知道以他的身份和经历能够合理知道的事"，然后逐条列出：

- 第一手领域（来自长期身在局中）；
- 情报渠道的滞后、误差与缺口；
- 只能推断、无法确知的事项；
- 不知道自己"原本的未来"；
- 不自动采信玩家的超时代知识。

收束句必须是 GM 可执行的临场自检："让他说出某条信息之前，先问一句：以他的身份、经历和开局年份，他为什么会知道这件事？"

### 3.3 必须显式标注的隐藏信息

以下内容在资产中出现时必须标注其暴露层级：

- 角色卡隐藏信息（私密事实、未公开动机）；
- 尚未发生的未来史实 / 默认轨迹；
- 系统 / 超自然私有信息；
- GM 后台计划性内容。

## 四、依赖与协同的自然语言表达

不使用任何机器依赖字段。资产间关系用以下三类写法表达。

### 4.1 可选性声明（世界包对世界内拓展包）

> 这些拓展包都是可选的。本世界包会在相关处提示配上哪个拓展包体验更完整，但建议只是建议：未启用时 GM 按本包给出的世界常识自然叙述即可，不需要假装机制存在，也不要静默替玩家启用任何东西。

### 4.2 协同 / 降级双写（拓展包之间）

每条协同关系必须同时写出"启用时获得什么"与"未启用时怎么办"：

> 本包的所有身体后果移交身体状态领域裁定。若同时启用《身体状态核心》，伤势会获得更细致的表现；未启用时 GM 按同样的区分直接裁定，本包规则依然完整可用。

### 4.3 归属指引（划清不拥有的领域）

用"X 属于《Y》"句式指出归属方，不建立依赖：

> 官职任免、势力博弈、合法性与外交的推演方式，属于《汉末三国：政争与势力》拓展包。

### 4.4 分级建议的写法

世界包可以提供 Required / Recommended / Optional 的自然语言分级清单（对齐 Game Composition 语义），但：

- 只写段落或列表，**不发明机器元数据字段**；
- 世界内部的 Source NPC、lore 不要求逐项选择，确认粒度是包级。

## 五、机制写作范式

机制不得拍平成纯 lore，也不得写成机器契约。

### 5.1 语义阶梯代替数值

用有序自然语言刻度，放在代码块中：

```text
未达成 → 有限达成 → 有效达成 → 优势达成 → 决定性达成
```

数值只在真正改善游玩时保留；禁止为数值而数值。

### 5.2 裁定写成 GM 的思考顺序

用箭头链表达自然的裁定流程，并声明不锁死公式：

```text
玩家意图 → 行动类别 → 能力基础 → 空间与条件 → 对抗反应 → 是否值得正式裁定 → 结果与后果移交
```

### 5.3 "何时才值得正式裁定"

每个机制包必须写明启用正式裁定的条件（真实不确定、成败有意义、合理可尝试、有对抗风险），防止裁定仪式化、防止琐碎行动被过度结算。

### 5.4 划界句

定义机制时用"X 不是 Y"句式同时立定义、堵误用：

> 压力是局势语言，不是血量换皮，也不是输入禁令。

### 5.5 长期状态清单与存储分离

- 拓展包只声明**哪些事实值得长期记住**（如关系变化、持续伤情、能力成长、未决后果）；
- **不得**声明存到哪里、什么文件、什么字段、什么格式——存储由 World Core 决定；
- 不得写"每回合请更新某某"之类的维护指令；durable maintenance 是 World Core 职责。

## 六、资产不写清单

以下职责属于 World Core / 宿主，资产正文一律不涉及：

- 开局向导、组合确认流程、Session 恢复逻辑；
- 每回合 durable change 维护指令、文件更新流程；
- 知识边界的执行机制（资产只标注，不控制传播）；
- 节奏状态机、操控粒度规则；
- 存档策略；
- 存储路径、实体 Schema、Manifest、校验器。

## 七、生产流程

### 7.1 批次生产（人物卡）

- 批次是生产次序，与优先级、复杂度三者分离；建议规模 10–15 张，不硬性封顶；
- 历史类资产族的批次按**主时代、次阵营**组织：一批专注一个时代段落中活跃或冒头的人物；角色多的时代再按阵营细分（汉末三国自 CC-BATCH-03 起实行，见各族生产规划）；
- 生产优先级分 S/A/B/C 四级，按对作品的重要性定，不等于卡片复杂度；
- 同批按对照关系交错生产（如交错势力），避免语料互相污染；
- 批次完成后做跨卡审核再开下一批。

### 7.2 单卡生产顺序

```text
题材与范围锁定
→ 史料 / 设定恢复
→ 证据分层（史实类资产用 S1/S2/I1/L1/C1）
→ 高密度压缩成卡
→ 决策生成性审核（是生成规则还是标签）
→ 玩家 / NPC 边界与知识边界审核
→ 终压与质量 Gate
```

### 7.3 Core-first 顺序

多资产共享同一机制时，先做通用核心（`拓展包/通用拓展包/`），再做世界专用下游；禁止先复制多份临时专用机制再事后抽取。发现第二个消费者时重新评估是否上提到通用资产库。

## 八、质量 Gate

每份资产完成后逐项自检；批次 / 整族任务另做跨资产审核。

### 8.1 单资产 Gate

- **身份与来源**：身份锚点清晰，史实 / 设定分层明确，未知处留白而非虚构；
- **密度优先，不设字数门槛**：不规定字数上下限，不做强制压缩。唯一的密度标准是：每节内容都要能改变 GM 的判断——无判断价值的内容删掉，有判断价值的内容不因为"太长"而机械压缩；卡片短也不是缺陷（未知优先于虚构）。百科化、论文化仍属反模式；
- **决策生成性**：人格是生成式决策结构，不是标签集合；
- **未来无污染**：不预写未来，原史 / 原设仅是参照；
- **知识边界**：信息暴露层级已标注，"凭什么知道"可回答；
- **玩家代理**：支持接管的卡写清 T0 前后归属；不替玩家预设重大承诺；
- **NPC 自主性**：NPC 有独立动机与判断，不是玩家 / GM 的功能件；
- **Life Loop 素材**：人物与世界提供了日常与非功能性互动面；
- **机制完整**：机制包保留可玩区分，未拍平成 lore，无数值恋物；
- **不越权**：未承担第 6 章任何宿主职责；
- **依赖表达**：全部为自然语言，协同关系有降级写法，Optional 不静默激活；
- **Source 纯洁**：无局内状态写法，无"运行时实例化"指令；
- **中文行文**：自然当代中文，历史概念用语恰当，无伪文言填充，无不必要的英文工程行话。

### 8.2 批次 / 整族 Gate

- 共享历史不重复（同一事件不在多张卡里各写一份互相矛盾的版本）；
- 关系对称（A 卡里的 B 与 B 卡里的 A 一致）；
- 声线收敛（同文化圈人物语言风格有区分度）；
- 名人标签核查（"奸雄""仁德"等后世标签不直接当人格真相）；
- 跨资产引用路径有效；
- 索引、版本锁、蓝图与本批次同步更新。

## 九、治理精简

保留的治理工件，全部为人工 Markdown 清单：

- **资产族成员索引**（`00_资产成员索引.md`）：纯路径聚合，指向 canonical 文件；
- **当前版本锁**（`03_当前版本锁.md`）：成员当前版本号清单；
- **资产组合总蓝图**（`01_资产组合总蓝图.md`）：保留 Canonical Ownership 分工、组成与启用分离语义；
- **批次索引**：Roster 表、人格差异冻结清单、关系登记（只冻结已发生历史，不冻结当前状态）。

同步废止的治理产物：

- Runtime Context Contract 及其索引、Sidecar 体系；
- 总蓝图中的 UI Surface Composition、G8→G9→Bundle 路线、"等待 G9"类免责注记；
- 批次索引中的机器依赖列、Binding 收口表；
- 一切"向未来机器架构提需求"的台账章节。

## 十、典型反模式

写作与审核时对照检查：

1. **百科卡**：把人物写成词条，什么都有一点、什么都没有判断价值；
2. **论文卡**：把考据过程写进正式卡（考据归 Research Note）；
3. **标签卡**：人格只有形容词，没有决策结构；
4. **剧本卡**：替人物预写未来选择；
5. **台词宏卡**：示例台词堆砌且被当成固定台词库；
6. **全能名人卡**：名人什么都会、什么都知道；
7. **机制拍平**：把机制深度删成纯描述，或反过来写成伪代码 / 数值契约；
8. **静默激活**：可选内容写得像默认开启；
9. **宿主越权**：资产里出现维护指令、存储指令、恢复指令；
10. **未来预写**：把原史结局写成世界必然。
