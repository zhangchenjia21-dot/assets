# 汉末三国：核心人物库生产规划 v0.1

> [!summary] 一句话结论
> 汉末三国人物库不追求“把所有有名字的历史人物都预制成角色卡”，而采用：
>
> **核心人物预制 Character Card + 情境人物按需制卡 + 背景人物由 Historical Baseline Resolver 保守实例化**
>
> 的分层策略。
>
> 人物卡负责“这个人是谁”，不负责保存逐年生涯快照；历史节点相关的官职、位置、既往关系、已发生事件等，由开局 Historical Baseline Resolver 按 `T0` 解析并锁入 Game State。

---

# 0. 文档定位

本文件是《汉末三国：天下未定》资产族的人物库生产规划。

它负责确定：

- 哪些历史人物值得拥有独立 Character Card；
- 哪些人物只需要 Resolver 在特定开局按需恢复；
- 人物库采用什么优先级与批次生产；
- 如何覆盖不同年代、不同政治集团、不同人物功能；
- 如何避免魏、蜀、吴热门人物挤占整个角色库；
- 如何避免人物卡互相复制历史事实；
- 如何组织 Research Note；
- 如何审核一批人物卡在一起时的跨卡一致性；
- 第一批正式人物卡生产哪些人物。

它**不负责**：

- 重写世界历史；
- 定义战争、政治、经济或恋爱机制；
- 创建具体 Game State；
- 设计 asset-spec Schema；
- 设计 Creator 页面；
- 预制全部三国人物。

---

# 1. 上位原则

本规划遵守以下已确认原则。

## 1.1 一人一卡

原则上：

> **一个历史人物只维护一个稳定 Character Definition。**

不创建：

- 184 年曹操卡；
- 200 年曹操卡；
- 208 年曹操卡；
- 220 年曹操卡。

不同开局年代的实际状态由：

```text
Character Card
+
World Pack
+
T0
+
Historical Baseline Resolver
↓
Historical Snapshot Candidate
↓
Bootstrap Validation
↓
Game State
```

产生。

---

## 1.2 人物卡不是人物百科

正式 Character Card 应优先保存：

1. 身份锚点；
2. 人格核心；
3. 能力与局限；
4. 决策与行为逻辑；
5. 关系风格与自主性；
6. 语言与表现；
7. Player Character 接管说明；
8. Historical Baseline Resolver Handoff。

详细史料、人格推断链、演义差异和争议论证进入：

> **Historical Character Research Note**

Research Note 不是 Runtime 资产。

---

## 1.3 当前动态状态不属于 Character Card

以下内容不得被预写成跨年代固定 Definition：

- 当前官职；
- 当前爵位；
- 当前所在势力；
- 当前所在地；
- 当前兵力；
- 当前伤势；
- 当前婚姻状态；
- 当前关系状态；
- 当前政治立场；
- 当前已经知道的全部信息；
- 当前声望；
- 当前任务。

这些属于 `T0` Historical Snapshot 或 Game State。

---

## 1.4 史料不足允许短卡

人物卡没有最低字数要求。

若可靠资料只足以支持：

- 身份；
- 一两个稳定评价；
- 少量能力轮廓；

则只写这些。

> **未知优先于虚构。**

---

# 2. 为什么不做“全人物预制库”

汉末三国具名历史人物极多。

若把每一个：

- 郡守；
- 县令；
- 小将；
- 谋士；
- 宗族成员；
- 使者；
- 地方豪强；

都预制成 Character Card，会产生几个问题。

## 2.1 维护成本失控

一旦需要维护数百张人物卡：

- Research Note 数量暴涨；
- 史料核查成本很高；
- 跨卡关系容易冲突；
- 同一历史事实会被大量重复引用；
- 用户几乎不会在多数游戏中遇到其中绝大部分人物。

## 2.2 低史料人物容易被过度创作

史料越少，越容易出现：

> 为了让角色卡“完整”，模型开始补人格、爱情观、口癖和战斗风格。

这会把同人创作静默伪装成历史人物 Definition。

## 2.3 Runtime 实际只需要局部高精度人物

不同开局时间与地点，真正需要高精度运行的人物数量有限。

因此更合理的是：

```text
高价值人物 → 预制 Character Card
↓
中等价值人物 → 按需求逐步制卡
↓
低频背景人物 → Resolver 保守实例化
```

---

# 3. 人物分级体系

人物库采用：

```text
S
A
B
C
```

四级。

这只是资产生产优先级，不是人物历史地位排行榜。

---


## 3.1 两个维度必须分离：生产优先级 ≠ 卡片复杂度

人物库存在两个不同维度：

### 生产优先级

```text
S / A / B / C
```

回答：

> 这个人物是否应该被优先预制成 Character Card？

### 卡片复杂度

例如：

```text
核心复杂人物
中高复杂人物
中等人物
稀疏人物
```

回答：

> 这张 Character Card 需要多少 Definition 密度与篇幅？

两者不得混用。

例如：

- 荀彧：A 级生产优先级，但可以是中高复杂人物；
- 鲁肃：A 级生产优先级，但可以是中等人物；
- 周瑜：S 级生产优先级，但卡片篇幅未必一定比所有 A 级更长。

### Batch 与优先级也必须分离

`CC-BATCH-01` 表示：

> 第一批实际生产批次。

它不是：

> “只包含 S 级”的批次。

第一批为了建立跨势力、跨功能的正式基准集，明确采用：

- 8 张 S 级；
- 4 张 A 级（荀彧、鲁肃、关羽、吕布）。

因此后续 `CC-BATCH-02` 的正确含义是：

> 补齐尚未生产的 A 级人物。

不是：

> “第二批出现的人才第一次被定义为 A 级”。

# 4. S 级｜核心枢纽人物

## 4.1 定义

满足多个条件：

- 能显著改变时代格局；
- 在较长历史区间保持高影响力；
- 可能成为大量不同开局的核心 NPC；
- 非常适合玩家接管；
- 人格和决策逻辑会显著影响世界走向；
- 与大量其他人物存在重要关系；
- 史料足以支持较稳定 Character Definition。

## 4.2 生产要求

- 优先独立 Character Card；
- 必须配套 Research Note；
- 必须经过较严格史料审核；
- 必须支持 NPC 与 Player Character 两种使用方式；
- 必须进行跨卡关系一致性审核；
- 需要特别检查大众文学形象是否污染正史 Definition。

## 4.3 当前 S 级候选

第一阶段候选：

- 曹操
- 刘备
- 孙权
- 孙策
- 袁绍
- 诸葛亮
- 司马懿
- 周瑜

后续可评估：

- 刘禅
- 曹丕
- 孙皓
- 司马昭
- 董卓

是否进入 S 级取决于后续资产需求，而不是一次性冻结。

# 5. A 级｜重要持续人物

## 5.1 定义

通常满足：

- 在一个重要势力或一个长阶段中具有显著作用；
- 经常可能成为玩家的重要盟友、上级、下属、敌人或互动对象；
- 有足够史料支持稳定人格或行为结构；
- 虽不一定是时代总枢纽，但其自主决策对局部世界非常重要。

## 5.2 生产要求

- 原则上制作独立 Character Card；
- 重要人物配 Research Note；
- 允许比 S 级明显更短；
- 不为人物历史地位强行扩充卡长；
- 优先按实际玩法需求生产。

# 6. B 级｜情境人物

## 6.1 定义

人物在：

- 特定地区；
- 特定年份；
- 特定政治事件；
- 特定战争；
- 特定人物关系网；

中很重要，但并不是大量开局都需要高精度长期运行。

例如某一地区的：

- 太守；
- 将领；
- 谋士；
- 宗族成员；
- 外交使者；
- 地方豪族。

## 6.2 生产策略

默认：

> **不提前批量生产。**

满足以下任一条件时再升格制卡：

- 被某个 World Pack 开局节点频繁激活；
- 与玩家长期互动；
- 进入重要关系链；
- 持续拥有独立目标和计划；
- 某个 Expansion Pack 需要高精度人物行为；
- Creator 用户主动选择将其升级。

# 7. C 级｜背景人物

## 7.1 定义

满足以下特点：

- 史料极少；
- 游戏中通常只是一次性或短期互动；
- 不需要长期高精度人格；
- 没有足够证据形成稳定 Character Definition；
- 为其制作完整角色卡的成本明显高于实际游戏价值。

## 7.2 默认处理

由：

> **Historical Baseline Resolver**

在需要时保守实例化。

只恢复：

- 身份；
- 当前年代已知职位；
- 所在地点；
- 与当前事件有关的事实；
- 极少量可靠人物评价。

人格未知处保持未知。

## 7.3 升格条件

若某 C 级人物在实际游戏中：

- 反复出现；
- 与玩家形成长期关系；
- 获得关键职务；
- 成为政治或军事核心；
- 玩家主动关注；

则 Game Runtime 可以把其 Game Instance 持续发展。

是否进一步反向制作正式 Character Card，属于 Creator / 资产生产行为，不由 Runtime 自动修改原资产。

---

# 8. 首批正式人物卡的目标

第一批不是为了“凑齐魏蜀吴代表队”。

主要目标是验证：

1. 多张 Character Card 同时存在时是否会产生事实重复；
2. 不同政治集团的人格是否仍然有独立辨识度；
3. 君主、谋臣、武将、联盟型人物是否都能使用同一短卡规范；
4. Player Character 接管规则是否适用于不同身份；
5. Research Note 是否会过度膨胀；
6. Historical Baseline Resolver Handoff 是否能够保持一致；
7. 跨卡关系是否能够通过 Resolver / Game State 而不是在人物卡中重复维护；
8. 是否存在必须反馈给 asset-spec vNext 的真实需求。

---

# 11. 为什么第一批暂不加入赵云、郭嘉等热门人物

不是因为他们不重要。

第一批优先覆盖：

- 君主；
- 继承统治者；
- 创业诸侯；
- 战略谋臣；
- 制度文臣；
- 武将；
- 联盟型人物；
- 高争议人物；
- 强大众形象偏差人物。

赵云、郭嘉、张辽、陆逊等更适合第二批。

如果第一批连这些更难的人物都能稳定运行，后续人物生产成本会明显下降。

---

# 12. 第一批生产顺序

不按势力批量生产。

建议按“对照关系”推进：

```text
1. 刘备
2. 袁绍
3. 孙权
4. 孙策
5. 诸葛亮
6. 司马懿
7. 周瑜
8. 荀彧
9. 关羽
10. 吕布
```

曹操与鲁肃已有实验卡，进入最后跨卡审核。

这样可以避免连续生成同一势力导致人物语气和价值结构互相污染。

---

# 13. 每张人物卡的生产包

每个正式人物默认生成：

```text
人物名__Character_Card__v0.1.md
人物名__历史人物研究附录__v0.1.md
```

若史料极少，Research Note 可以非常短。

# 16. 跨卡审核维度

## 16.1 Shared History Duplicate Gate

检查人物卡是否复制：

- 战争事实；
- 政治格局；
- 当前官职；
- 当前人物关系；
- 当前势力状态。

发现后：

> 优先删除人物卡中的时间状态，交回 World Pack / Resolver / Game State。

---

## 16.2 Relationship Symmetry Gate

人物关系具有方向性。

例如：

> 曹操如何看刘备

不必等于：

> 刘备如何看曹操。

人物卡不能通过一句：

> “二人互相欣赏又互相忌惮”

把两人的方向性关系锁死。

稳定历史关系只做 Handoff。

当前关系由 `T0` Resolver / Game State 决定。

---

## 16.3 Voice Convergence Gate

检查不同人物是否被写成：

> 同一个聪明政治家的不同名字。

尤其要比较：

- 曹操 vs 袁绍；
- 刘备 vs 孙权；
- 诸葛亮 vs 荀彧；
- 鲁肃 vs 周瑜；
- 关羽 vs 吕布。

如果他们面对相同问题总会给出相同答案，则 Definition 信息密度不足。

---

## 16.4 Famous Label Gate

禁止以下标签直接成为全部人格：

- 曹操 = 奸雄
- 刘备 = 仁德
- 袁绍 = 优柔寡断
- 诸葛亮 = 神机妙算
- 司马懿 = 隐忍
- 周瑜 = 嫉妒
- 关羽 = 忠义
- 吕布 = 有勇无谋

标签可以作为后世评价研究材料。

不能取代生成式决策结构。

---

## 16.5 Future Contamination Gate

重点检查：

- 司马懿是否因为晋朝出现被写成必然夺权；
- 曹操是否被提前写成必然篡汉；
- 刘备是否必然建立蜀汉；
- 孙权是否必然称帝；
- 诸葛亮是否必然北伐；
- 关羽是否必然失荆州。

全部必须为：

> `T0` 后开放未来。

---

## 16.6 Player Character Agency Gate

若玩家接管历史人物：

- 过去锁定；
- 未来开放。

尤其检查：

- 忠诚；
- 称帝；
- 联盟；
- 背叛；
- 杀人；
- 婚姻；
- 爱情；
- 人生目标；

是否被历史结果偷偷写成强制。

---

## 16.7 Runtime Density Gate

检查：

- 是否存在重复人格说明；
- 是否把证据全文复制进 Character Card；
- 是否有可删除的“人物百科”内容；
- 是否存在只适用于一个历史事件的脚本规则。

# 20. Historical Baseline Resolver 对人物库的需求

人物卡生产已经暴露以下未来平台需求。

## HR-01｜身份消歧

Resolver 必须能够利用：

- 规范姓名；
- 字；
- 籍贯；
- 出生年份或范围；
- 基础历史身份；

避免搜索同名人物。

---

## HR-02｜T0 截止

查询必须明确：

> **截至 T0 已经发生什么。**

而不是：

> 介绍这个人的一生。

---

## HR-03｜未来污染防护

Resolver 必须区分：

```text
T0 前
= 可成为历史基础事实

T0 后
= 只供现实历史参考
```

---

## HR-04｜Unknown / Disputed

Resolver 成功输出必须允许：

- unknown；
- disputed；
- approximate；
- insufficient evidence。

不能要求所有字段都有值。

---

## HR-05｜来源层级

至少需要区分：

- 正史正文；
- 注引材料；
- 编年互证；
- 后世史论；
- 文学；
- 现代二手资料。

具体机器结构留给 asset-spec vNext。

---

## HR-06｜Bootstrap 锁定

一旦历史快照被确认进入 Game Instance：

> Save / Restore 使用锁定快照。

不能恢复存档时重新联网生成另一份过去。
