# 乱世三国｜制图生产经验与 AI 协作规范

## 0. 目的

本文件收敛 Level 1 天下图、L2-01 关中—弘农—雒阳、L2-02 荆襄—江汉连续生产中已经验证的工作经验。

它不是新的历史事实源，也不替代各地图 Data Owner；它负责回答：

> **以后如何更快、更稳地设计、生成、审核并冻结地图美术资源。**

核心目标：减少重复规划、避免 AI 图像模型重新决定历史事实、避免因追求理论完美造成无止境返工。

---

## 1. 已验证的总体原则

### 1.1 Fact Space 与 Artwork Space 永久分离

Fact Space 负责：

- 历史身份；
- 山河拓扑；
- 城邑相对关系；
- 行政与时代信息；
- 道路 / 水路 / 门户事实。

Artwork Space 负责：

- 16:9 画布；
- 游戏化舒展；
- 标签安全区；
- 叙事空间放大；
- 局部压缩；
- 最终视觉锚。

已经验证：

> **拓扑正确、叙事关系正确，比严格 GIS 比例更重要。**

允许局部舒展，但不得改变城市顺序、山河两侧关系、门户控制关系和区域出入口。

### 1.2 Level 1 与 Level 2 使用不同信息预算

Level 1 天下图承担全局认知，因此需要较强留白与信息压缩。

Level 2 区域图承担旅行、交通、生活与剧情，因此可明显增加：

- 次级城邑；
- 道路；
- 水路；
- 渡口 / 港口；
- Narrative 节点；
- 地方性自然地理；
- 农田 / 湿地 / 聚落环境。

重要区域可采用 `high-density-important-region`：

- 2K 画布优先保证真实可读字号；
- 不因对象增加而整体缩小所有文字；
- 提高“叙事与交通信息密度”，不提高“行政百科密度”。

L2-02 已验证：重要地区比 L2-01 更高密仍可保持清晰。

### 1.3 不是所有区域都需要同一种密度

区域图应先选择 density profile：

- `standard-region`：一般区域，强调清楚、留白；
- `high-density-important-region`：中原、荆襄、江东、巴蜀核心等高频叙事区；
- `corridor-region`：关中—弘农—雒阳这类走廊型区域；
- 其它 Profile 只有在真实生产需要时再增加。

不要因为模板存在就机械复制固定数量。

## 2. 参考资料的职责必须拆分

一张历史地图通常不能同时承担：历史事实、自然地理、最终构图和美术风格四种职责。

推荐拆分：

- 历史行政 / 城邑图：提供城邑、道路、行政、相对位置参考；
- Level 1 已批准地图：提供上位拓扑与视觉 DNA；
- 区域专项资料：只解决真实 blocker；
- AI 区域底图：只负责 Regional Artwork Space 的视觉实现。

不要因为参考图只覆盖区域一部分，就误以为项目范围必须跟随参考图裁切。

不要把历史行政图直接描成玩家地图。

## 3. AI 生成底图的关键经验

### 3.1 图像模型会放大语义词，需要用“比例与层级”约束

L2-02 v001 已验证：仅写“云梦复合湿地、水网、湖沼、洲滩”容易被模型误读为：

> 大面积永久水面 + 数百小岛 + 千岛湖式群岛。

因此以后涉及水乡 / 湿地 / 湖网必须同时写：

> **水网丰富 ≠ 水面占多数。**
>
> **湿地平原 ≠ 群岛。**

并明确：

- 连续陆地必须占主导；
- 哪些区域必须保留稳定陆地；
- 主河 / 次河 / 水渠的视觉等级；
- 湖泊和湿地的相对面积；
- 哪些区域为未来城市 / 标签预留。

同理，涉及山地时也要明确：

> 山地重要 ≠ 满屏碎山。

### 3.2 无字底图本身必须为 Overlay 服务

R4 不只验“好不好看”，还要验：

- 是否有足够稳定陆地放城市；
- 是否有道路可以真实穿过的谷地；
- 河流是否有明确主次；
- 是否预留城市群 / 标签安全区；
- 是否允许高密 Overlay 而不破坏地理。

底图若只能通过“城市上岛、道路穿山、标签压满山峰”才能使用，应在 R4 判失败，而不是把问题推到 R5。

### 3.3 结构性失败与局部问题必须区分

需要重新生成 R4 的情况：

- 地理拓扑错误；
- 大尺度水陆比例错误；
- 主要城市区域没有稳定落位空间；
- Narrative 主轴无法成立；
- 视觉结构与任务类型根本不符。

不应重新生成底图的情况：

- 一个标签偏几十像素；
- 一个次级城市 Anchor 需要移动；
- 道路线宽偏弱；
- 城市 / Narrative 标签碰撞；
- Display Name 需要调整。

后者应做确定性 Overlay 修订，避免“修一个字重新生成整张地图”。

## 4. 描点与 Overlay 的生产经验

### 4.1 R5-A 与 R5-B 可以合并给执行型 AI

L2-01 与 L2-02 已验证：对象数量可控时，可以让外部执行型 AI 一次完成：

1. 内部 Regional Anchor Calibration；
2. 开发审核图；
3. 正式 Overlay。

但必须要求同时输出 `Anchor Review`，以便技术审核 AI 检查拓扑，而不是只看漂亮成图。

### 4.2 正确 Anchor 优先于标签位置

事实 / Artwork Anchor 正确后：

- 标签可上下左右偏移；
- 必要时使用短 leader line；
- 不为了排文字移动核心事实点。

### 4.3 正式中文必须可控

正式资产原则仍为：

- 使用真实中文字体 / 可编辑文字层；
- 不接受 AI 伪汉字；
- 城市、战略点、山河、行政背景需要不同视觉层级。

如果外部执行工具能确定性排字，可一次完成；否则底图生成与正式文字必须分离。

## 5. 历史对象与玩家 Display Object 分离

已经验证，玩家地图不应被迫只使用一种命名语义。

数据层建议区分：

- `historical_identity`：历史事实对象；
- `display_name`：玩家地图显示名；
- `display_role`：玩家认知职责；
- `historical_parent`：历史行政归属；
- `display_macro_state / display_region`：游戏显示归属。

案例：

- Level 1 可隐藏“豫州”大标签，但历史豫州继续存在；
- 临湘可以作为历史城邑保留，同时允许“长沙”作为玩家熟悉的区域 Display Object；
- 江夏郡、夏口、沙羡不能被自动排版模型合并成一个同级地点。

原则：

> **不要为了玩家熟悉度改写历史事实；也不要为了历史术语纯度牺牲游戏识别。**

二者通过数据角色分离解决。

---

## 6. 水路与交通审核不要过度收紧

Artwork Space 下，叙事“水路枢纽”不等于要求城市点精确压在数学意义的汇流像素上。

审核优先看：

- 网络是否连通；
- 河流层级是否明确；
- 城市是否能通过合理水路 / 陆路到达；
- 渡口 / 港口是否控制正确交通；
- 玩家是否会产生错误方向认知。

不要把“交通网络成立”错误收紧成“必须与现代精确水系线逐像素重合”。

---

## 7. 审核哲学：硬错误与软偏好分开

### 7.1 Hard Blocker

只有以下问题应阻塞 Gate：

- 拓扑错误；
- 历史身份 / 角色冲突导致玩家被误导；
- 主城市或门户位于明显错误地形；
- 道路穿越不可能地形；
- 核心文字不可读；
- 正式资产存在伪字、水印或明显导出错误；
- 底图被 Overlay 阶段意外重新生成 / 改写。

### 7.2 Soft Issue

以下通常不应造成新一轮全图返工：

- 轻微比例失真；
- Narrative 点几十像素级位置差；
- 道路稍淡；
- 某个州 / 郡 / 山河文字略偏；
- 不影响阅读的局部密度差异。

原则：

> **游戏逻辑能讲通、主要地理大致正确、2K 可读，即可进入下一阶段。**

不追求“百分比完美”。

## 8. 已冻结成果对后续地图的意义

### 8.1 Level 1 天下图

天下图已经承担了最高成本的“空间宪法”工作：

- 16:9 Player Geometry；
- Fact / Artwork 分离；
- 核心城市大尺度关系；
- 一级山河；
- 视觉 DNA；
- 基础文字 / 符号语言。

Level 2 不再重复这套完整 Gate 链。

### 8.2 L2-01｜关中—弘农—雒阳

验证了：

- `corridor-region`；
- 平原 → 门户 → 狭道 → 平原；
- 以陆路、关隘、山河控制为主；
- R5-A + R5-B 可合并执行。

### 8.3 L2-02｜荆襄—江汉

验证了：

- `high-density-important-region`；
- 水陆复合交通；
- 复合湿地如何避免群岛化；
- 18+ 地点、Narrative 节点、行政背景可在 2K 同时存在；
- 历史名与玩家 Display Name 可以分角色处理。

## 9. AI 协作角色分离

### 9.1 Owner

Owner 负责：

- 最终产品取舍；
- 接受游戏化形变；
- 选择是否保留 / 删除对象；
- 对争议命名和玩家熟悉度作最终裁决；
- 决定 Gate 是否接受。

Owner 明确决定 supersede 旧工作建议。

### 9.2 技术设计 / 架构 / 审核 AI

本角色**不承担生图**。

职责：

- 读取仓库 Authority；
- freshness / superseding decision 检查；
- 定义地图范围；
- 设计 Narrative 主轴；
- 维护对象清单与数据结构；
- 设计 Regional Artwork Space 约束；
- 历史与拓扑审核；
- 信息密度与文字架构；
- 输出给外部生图执行器的任务 Prompt；
- 审核外部产出；
- 判断 PASS / CONDITIONAL PASS / FAIL；
- 写回规范、Data Owner、Gate、交接文档。

禁止：

- 直接调用图像生成模型制作项目资产；
- 直接编辑项目底图；
- 因为“可以生图”而跳过设计与审核。

### 9.3 图像执行 AI / KIMI

职责：

- 按技术规范生成 / 修订底图；
- 按冻结对象做描点；
- 制作 Anchor Review；
- 制作正式 Overlay；
- 输出 PNG / SVG / JSON 等资产。

不得：

- 自行重写历史事实；
- 自行改变 Owner 冻结对象；
- 自行决定新的产品规则；
- 在 Overlay 阶段擅自重生成已经冻结的底图。

## 10. 推荐标准协作流程

```text
技术设计 AI
→ 读取 Authority / freshness
→ 定义 R0–R3 / 输入规范
→ 写给图像执行 AI 的 R4 Prompt

图像执行 AI
→ 生成 R4 无字底图

技术设计 AI
→ R4 Gate
→ 只区分结构性失败 / 局部问题

图像执行 AI
→ R5-A Anchor Review + R5-B 正式 Overlay

技术设计 AI
→ 拓扑、信息层级、历史角色、可读性审核
→ Owner Review
→ Gate / Repo 写回
```

同一聊天不需要同时承担“设计者、生成器、审核者”三种冲突角色。

---

## 11. 资产卫生

正式冻结前检查：

- 无水印；
- 无“AI生成”等平台标记；
- 输出尺寸与元数据一致；
- 正式文字无伪字；
- SVG / Overlay 依赖关系明确；
- JSON 中 historical / display 角色不互相覆盖；
- 开发 Debug 层不进入玩家版；
- 原始无字底图与 Overlay 可分离维护。

Pilot 阶段可以接受较低分辨率验证构图，但正式导出应尽量使用真实 2K 或更高母版。

## 12. 当前后续方向

Level 2 已通过两种 Pilot 类型后，后续区域不再以“再次验证模板”为目的，而应直接生产内容。

当前下一高价值候选：

> **兖州—豫州—青州—徐州高密度区**

该区域预计属于 `high-density-important-region`，重点将从荆襄的水陆湿地网络转向：

- 黄河—济水 / 淮水等平原水系；
- 中原高密城邑；
- 官渡、陈留、许、濮阳、谯、彭城、下邳等政治军事节点；
- 青徐沿海 / 山东丘陵与平原过渡；
- 多州行政背景与玩家显示层的解耦。
